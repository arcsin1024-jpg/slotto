## できたこと

### 予約の作成と操作(`@/server/booking`)

スタブの関数名と引数はそのまま。

| 関数 | 内容 |
|---|---|
| `createBooking(input)` | 予約ページと設定を読み、`isSlotAvailable` で枠を確かめ直してから、DB の関数 `create_booking` で書く。承認制なら `pending` |
| `approveBooking(hostId, id)` | `pending` → `confirmed`。そのあと確定の後処理 |
| `declineBooking(hostId, id, reason?)` | `pending` → `declined`。ゲストにメール |
| `cancelBooking({by:"host"...} \| {by:"guest", token}, reason?)` | ホストは期限に関係なく(終わった予約は不可)。ゲストは期限と `allow_guest_cancel` を守る |
| `rescheduleBooking(token, startsAt)` | 元の予約を空きに含めずに計算し直し、1 つのトランザクションで「元を取り消し → 新しい予約を作る」 |

- ふさがっている時間 = 同じホストの有効な予約 + `external_events` の **`is_selected = true` の予定だけ**
- 1 日の上限は、その予約ページの予約だけを数える(TimeRex と同じ。リサーチ 2 章)
- 1 回限りの予約ページは、予約が入ったら `is_active = false`。閉じたあとも、その予約の日程変更はできる
- ホストの操作は、予約の `host_id` と `hostId` が一致するかを必ず確かめる
- 状態の変更は条件付きの UPDATE 1 文(承認とキャンセルが同時に来ても片方だけ通る)
- 確定後の後処理(`side-effects.ts`): カレンダー書き込み(会議 URL を予約に保存)→ メール → `scheduleBookingJobs` → `triggerBookingAutomations` → ホストへのプッシュ。**どれが失敗しても予約は失敗させず**、ログに出して `booking_events` に `failed` を残す
- 操作ごとに `booking_events` に履歴(created / approved / declined / cancelled / rescheduled / calendar_written / email_sent / reminder_sent / failed)
- ゲスト向けの読み出しも追加: `getPublicPage`、`getPublicSlots`、`getPublicBooking`、`getPublicProfile`、`toPublicBooking`(返す形は `apps/web/src/features/booking/types.ts`)

### マイグレーション(`supabase/migrations/20261003000000_create_booking.sql`)

- 関数 `create_booking(...)`: ホスト単位のアドバイザリロック → 前後の空きを含めた重なり(予約 + 反映中の外部予定)と 1 日の上限を確かめ直す → 挿入。排他制約に当たったら `slot_taken`。日程変更、1 回限りの予約ページを閉じる処理、履歴の記録も同じトランザクション
- `booking_events.type` に `email_sent` と `failed` を追加
- service_role だけが実行できる

### API

| エンドポイント | 内容 |
|---|---|
| `GET /api/public/pages/{username}/{slug}` | 予約ページの公開情報 |
| `GET /api/public/pages/{username}/{slug}/slots?from&to&reschedule=<token>` | 空き枠(UTC)。最長 62 日。`reschedule` で元の予約の時間も空きとして出す |
| `POST /api/public/bookings` | 予約の作成(`createBookingInputSchema`) |
| `GET /api/public/bookings/{token}` | 予約の確認 |
| `POST /api/public/bookings/{token}/cancel` | キャンセル(`{ reason? }`) |
| `POST /api/public/bookings/{token}/reschedule` | 日程変更(`{ starts_at }`)。新しい予約(新しいトークン)を返す |
| `GET /api/public/bookings/{token}/ics` | 「カレンダーアプリに追加」用の .ics(確定した予約だけ) |
| `POST /api/bookings/{id}/approve` `…/decline` `…/cancel` | ホスト用。`getApiUser` で本人確認(Cookie / Bearer) |

- エラーは `{ error: { code, message } }`。`not_found` 404、`invalid` 400、`forbidden` 403、`slot_taken` 409、`too_late` 422、回数制限 429
- 公開 API の回数制限: 読み出し 120 回/分、書き込み 10 回/分(IP ごと、サーバーのメモリ上。インスタンスをまたいだ合計ではない)

### メール(`@/server/email`)

- `sendBookingEmail(kind, bookingId, options?)`。第 3 引数(送る相手など)は省略可能で、S4 の呼び方は変わらない
- Resend の API を `fetch` で呼ぶ(パッケージは足していない)。`RESEND_API_KEY` が無ければ内容をログに出すだけ。冪等キーは「予約 ID + 種類 + 相手」(リマインドは 10 分単位の時刻も含める)
- ゲスト宛てに .ics を添付: 確定・日程変更・リマインドは `METHOD:REQUEST`、確定していた予約のキャンセルは `METHOD:CANCEL`。UID は日程変更でつながる最初の予約の ID、SEQUENCE は「2 × 世代(+1 で取り消し)」で常に増える
- 文面は日本語。ゲスト宛てはゲストのタイムゾーン、ホスト宛てはホストのタイムゾーン。ゲスト宛てに `/b/{manage_token}` のリンク、ホスト宛てに回答内容
- ホスト宛ては `user_settings.email_on_booking` / `email_on_cancel` に従う(承認のお願いとリマインドは常に送る)
- 承認待ちの予約のメールには、会議 URL や住所を載せない

### S3(カレンダー)

- `writeBookingEvent` の戻り値で、S2 が `bookings.provider_event_id`、`provider_calendar_id`(予約ページの `write_calendar_id`)、`meeting_url` を保存している。S3 側でも保存していて構わない
- 日程変更は「新しい予約を作り、元を取り消す」ので、`updateBookingEvent` ではなく、元の予約に `deleteBookingEvent`、新しい予約に `writeBookingEvent` を呼ぶ。`deleteBookingEvent` は `provider_event_id` がある予約にだけ呼ぶ
- ゲストを Google の予定の参加者に入れて招待を送る(`sendUpdates=all`)と、Slotto が送る .ics と二重になる。参加者に入れる場合は知らせてほしい(.ics の UID を Google の `iCalUID` に合わせる)

### S4(実行基盤)

- `sendBookingEmail("booking_reminder", id)` は、ゲストとホストの両方に送る。確定していない・開始済みの予約には送らない
- `triggerBookingAutomations("booking_created")` は確定したとき(即時確定、または承認)だけ呼ぶ。承認待ちと日程変更では呼ばない。`"booking_cancelled"` は確定していた予約のキャンセルのときだけ
- `sendPush` をホスト宛てに呼ぶ: 新しい予約、承認待ち、日程変更、ゲストによるキャンセル。`data` は `{ type: "booking", id }`
- 日程変更では、元の予約に `cancelBookingJobs`、新しい予約に `scheduleBookingJobs` を呼ぶ

### S5(管理画面)

- 承認・辞退・キャンセルは `@/server/booking` の関数を Server Actions から呼べる(戻り値の `ok` / `code` / `message` をそのまま表示に使える)
- 日程変更された元の予約は `status = cancelled` で、`booking_events` に `rescheduled`(`data.to` が新しい予約の ID)が残る。新しい予約は `rescheduled_from` を持つ
- ホスト宛てのメールのリンクは `/app/bookings?id=<予約 ID>`。この形で詳細を開けるようにしてほしい
