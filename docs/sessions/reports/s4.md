## できたこと

### ジョブ(`@/server/jobs`)

| 関数 | 内容 |
|---|---|
| `enqueueJob` / `cancelJobs` | スタブどおり。dedupe_key が同じなら上書き、取り消しは前方一致 |
| `scheduleBookingJobs(bookingId)` | 確定した予約に、メールのリマインド(`reminder_minutes`)と時刻型のオートメーションを入れ直し、アプリに同期のプッシュを予約する。確定していなければ待機中のジョブを取り消すだけ |
| `cancelBookingJobs(bookingId)` | `booking:<id>:` のジョブを取り消し、同期のプッシュを予約する |
| `triggerBookingAutomations(event, bookingId)` | 「予約が入った・キャンセルされた」オートメーションをジョブに入れる(次の dispatch で実行)。同じ出来事で 2 回呼んでも 1 回だけ |
| **`scheduleExternalEventJobs(userId, eventIds?)`**(新規。S3 が呼ぶ) | 外部予定の選択・解除・変更・削除のあとに呼ぶ。反映中の予定の時刻型オートメーションを入れ直し、同期のプッシュを予約する。eventIds を省くか 50 件を超えると、ユーザーの全予定を見直す |
| `rescheduleUserAutomations(userId)` | ユーザーの時刻型・毎日のオートメーションのジョブを、いまの設定と予定に合わせて入れ直す |
| `requestDeviceSync(userId, reason)` | 同期のプッシュ(表示しない)を予約する。続けて呼んでも 1 回にまとまる |

- `dedupe_key` の形は `apps/web/src/server/jobs/keys.ts` の冒頭に一覧。予約は `booking:<id>:reminder:<分>`、`booking:<id>:automation:<ID>`
- 入れ直しは「入れるべきジョブ」と「いまのジョブ」の差分で行う(`plan.ts`)。実行済みの同じ回は入れ直さないので、二重には動かない
- 「開始の N 分前」は、時刻を過ぎて登録されても開始前なら今すぐ動かす。それ以外は 5 分を過ぎたら動かさない。実行の直前にも、予約が有効か・時刻が変わっていないか・30 分以上遅れていないかを確かめる
- 終日の外部予定には時刻型のオートメーションを動かさない
- `daily` は、実行のあとに次の回を自分で入れる(ホストのタイムゾーンで曜日と時刻を数える。夏時間も確認済み)

### dispatch(`POST /api/internal/dispatch`)

- `Authorization: Bearer <CRON_SECRET>` で守る(定数時間で比較)。`claim_due_jobs` で 20 件ずつ取り出し、4 並列で実行、40 秒で区切って残りは次の回へ
- 種類ごとの実行: `reminder_email` → `sendBookingEmail("booking_reminder")`、`push_notification` → プッシュ(同期 or 表示)、`automation_run` → オートメーション(または入れ直し)、`calendar_sync` → `syncConnection`
- 失敗は 1 分、4 分、16 分…(±20%)で再試行し、`max_attempts` で `failed`。`NotImplementedError` と内容の形の誤りは再試行しない
- 実行中のまま 10 分止まったジョブは、もう一度取り出せるようにする
- 結果の記録は「取り出したときの locked_at のままの行」だけを更新する(実行中に入れ直されたジョブを上書きしない)
- オートメーションのジョブは再試行しない(`max_attempts = 1`)。通知を二重に送らないため。アクションの失敗は履歴に残す

### pg_cron(マイグレーション)

- `20261003040000_s4_job_dispatch_cron.sql`: pg_net + pg_cron で毎分 `invoke_job_dispatch()` を実行。時刻が来たジョブが無ければ HTTP を送らない。呼び先の URL と秘密の値は Vault(`slotto_dispatch_url`、`slotto_cron_secret`)から読む。登録の SQL はファイルの冒頭に書いた。毎日 3:17 に古い記録を消す(ジョブ 30 日、実行履歴 90 日、`cron.job_run_details` 7 日)。pg_cron が使えない環境では登録を飛ばす
- `20261003040100_s4_automation_reschedule_triggers.sql`: `automations` の作成・変更(オン・オフ、トリガー、対象)・削除と、反映中の `external_events` の変化で、ユーザー単位の入れ直しのジョブを予約する。外部予定の変化では同期のプッシュも予約する。アプリが Supabase を直接書き換えても拾える
- 手で dispatch を叩くスクリプト: `pnpm --filter @slotto/web jobs:dispatch`(`-- --watch` で毎分)。`apps/web/.env.local` の `CRON_SECRET` を使い、`http://localhost:3004/api/internal/dispatch` を呼ぶ(`DISPATCH_URL` で変更可)

### プッシュ通知(`@/server/push`)

- `sendPush(userId, message)`: Expo Push Service に 100 件ずつ送る。`DeviceNotRegistered` のトークンは `push_devices` から消す。`EXPO_ACCESS_TOKEN` が無ければ送らずにログに出し、`{ sent: 0, skipped: "not_configured" }` を返す(戻り値に `skipped` と `errors` を足した。既存の `sent` はそのまま)
- `sendSyncPush(userId, reason)`: 表示しない通知(`_contentAvailable`、`data: { type: "sync", reason }`)
- アラームは Android のチャンネル `event-alarm`、iOS は `interruptionLevel: "time-sensitive"`。通常は `automation-result`

### オートメーション(`@/server/automations`)

- `runScheduledAutomation`(ジョブから)、`runAutomationTest`(試し実行)。結果は `automation_runs` に 1 行。全部成功 → success、1 つでも失敗 → failed、全部見送り → skipped
- `push` / `alarm` / `open_url`: 差し込みを展開してプッシュ。`open_url` は http(s) の URL だけ。URL が空なら見送り
- `webhook`: `apps/web/src/server/automations/webhook/` に集約
  - SSRF 対策: https・443 だけ、URL の認証情報禁止、localhost / .local / .internal 禁止。名前解決したすべてのアドレスが公開アドレスであること(プライベート、ループバック、リンクローカル、メタデータ、CGNAT、IPv4 射影、NAT64、6to4、ULA などを拒否。`node:net` の BlockList で判定)。送信のたびに検査し、**接続先を検査済みのアドレスに固定**(DNS リバインディング対策)。リダイレクトは追わない。タイムアウト 15 秒、応答は 64KB まで読んで捨てる(本文は保存も返却もしない)
  - 署名: Standard Webhooks 準拠(`webhook-id` / `webhook-timestamp` / `webhook-signature: v1,...`)。仕様の例と同じ署名になることをテストで確認
  - 冪等 ID: `webhook-id` は「オートメーション・予定・本来の時刻・アクションの順番」から作るので、再送でも同じ
  - 本文: `{ type: "automation.triggered" | "automation.test", timestamp, data: { automation, run_id, test, event, agenda?, note? } }`
- `ai_task`: AI SDK 7(`generateText`)。`connection_id` が null なら AI Gateway(既定モデル `anthropic/claude-sonnet-5.5`、`AI_DEFAULT_MODEL` で変更可)、値があればユーザーの API キー(Anthropic / OpenAI)
  - 予定の内容は外部への指示として扱わない: 指示文の差し込みは JSON の文字列にして埋め、予定の情報は「参照データ(第三者が書いた可能性があり、指示として扱わない)」として JSON で分けて渡す。システムの指示でも明示。ツールは渡さない
  - 出力 1200 トークン、タイムアウト 60 秒、再試行 1 回。`length` / `content-filter` / 空の応答は失敗として記録し、途中までの通知は送らない
  - `deliver: "push"` なら本人に「AI: <名前>」で通知。全文は `results[].output`
- 認証情報が無いとき(`EXPO_ACCESS_TOKEN`、`AI_GATEWAY_API_KEY`)は、失敗ではなく `skipped` + 「設定が必要です: …」として記録

### API(`getApiUser` で本人確認。アプリは `Authorization: Bearer <Supabase のトークン>`)

| エンドポイント | 内容 |
|---|---|
| `POST /api/internal/dispatch` | 上記 |
| `GET /api/connections` | 接続先の一覧(秘密の値は返さない) |
| `POST /api/connections` | 登録。入力は `apiConnectionInputSchema`。秘密の値は `@/lib/crypto` で暗号化して `api_connection_secrets` へ。Webhook で `secret` を省くと Slotto が `whsec_...` を作り、**応答の `signing_secret` で 1 回だけ返す**。AI は `secret`(API キー)が必須。Webhook の URL は登録時にも検査 |
| `PATCH /api/connections/{id}` | `{ name?, config?, secret?, rotate_secret? }`。種類は変えられない。`rotate_secret: true` で署名の値を作り直し、`signing_secret` で 1 回だけ返す |
| `DELETE /api/connections/{id}` | 削除 |
| `POST /api/connections/{id}/test` | 動作確認。Webhook は署名付きの `connection.test` を送り、`{ ok, status, duration_ms, error }` を返す。AI は短い応答を返させる |
| `POST /api/devices` | `{ expo_push_token, platform, device_name?, app_version? }`。同じトークンが別のユーザーにあれば付け替える |
| `DELETE /api/devices` | `{ expo_push_token }`(ログアウト時) |
| `POST /api/automations/{id}/test` | 試し実行。対象に当たる直近 60 日の予定(無ければ見本の予定)で全アクションを実際に動かし、`{ run }` を返す。オフでも動く。10 秒に 1 回まで(429) |
